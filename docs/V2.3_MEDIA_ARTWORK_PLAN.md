# v2.3 Media Artwork & Metadata Manager Plan

## Status

**v2.3 build started 2026-09-25.**

First implementation now includes the shared browser artwork-manager core, Media-library and film-page **Edit artwork** entry points, combined Wikipedia/Wikimedia Commons artwork search, IMDb title-link recognition through the title's IMDb ID, candidate preview/selection, manual image URL, local image selection, crop/position controls, IndexedDB persistence/locking, and Reset to Automatic. Acceptance remains subject to maintainer validation.

## Goal

Add a maintainer-facing artwork workflow inspired by Plex artwork editing while preserving Hanafi Media's local IndexedDB artwork architecture.

## Planned artwork workflow

From a movie or future TV-show page, **Edit Artwork** opens an artwork manager that can:

- show the current poster and alternate artwork candidates;
- search again using title, year, media type and external IDs when available;
- preview candidates in the actual Hanafi card frame;
- accept a searched candidate with **Use this artwork**;
- accept a manually entered image URL;
- accept a local JPG, PNG or WebP chosen from the maintainer's device when metadata/artwork cannot be found or is undesirable;
- provide zoom/crop and X/Y positioning before acceptance;
- save the accepted result to IndexedDB for reuse;
- mark a manual selection as locked so automatic refresh cannot silently replace it;
- provide **Reset to Automatic** when the maintainer intentionally wants matching/search to take control again.

A failed metadata match must never leave the maintainer trapped with a blank card. Manual artwork is a first-class fallback.

## Proposed metadata model

Each title should have a stable record with fields for:

```text
id
type: movie | tv
title
originalTitle
year
externalIds
artwork:
  mode: automatic | selected | local
  selectedSource
  cacheKey
  locked
  crop:
    scale
    x
    y
editions[]
details
ratings
links
```

## Local artwork handling

When a local image is selected, the browser should normalize its orientation, let the maintainer crop/position it, resize it to a practical poster resolution, encode a compressed WebP copy when supported, and store the resulting Blob in IndexedDB. The original movie/video file is never modified.

Poster binaries are not to become a growing GitHub artwork collection. GitHub stores the application and default metadata; maintainer-selected image bytes remain local unless a later explicit export/synchronization feature is approved.

## TV-ready architecture

The first implementation may operate on the current movie library, but the artwork component and metadata record must support `movie | tv` from the beginning. Future series posters, season posters and episode thumbnails should extend the same system rather than creating a second artwork manager.

## Persistence

Manual artwork and crop choices must survive normal reloads and Web App updates. Existing v2.2 IndexedDB artwork should migrate or fall back cleanly.

A later optional export/import feature may make customized artwork settings portable between the maintainer's devices. It must not require an account or behavioral tracking.

## Acceptance tests

- Search returns identifiable artwork candidates for a known title.
- Selecting a candidate changes the card and survives reload.
- Manual image URL works.
- Local image selection works.
- Crop/position preview matches the final card.
- Manual selection is not overwritten by automatic refresh.
- Reset to Automatic works.
- Missing metadata can still be given artwork manually.
- Existing v2.2 cached posters continue working or migrate safely.
- Card and list views continue to open the same title.
- Mobile and desktop artwork controls remain usable.
- Existing DK Media playback controls remain unchanged.

## First-build non-goals

- no Plex dependency;
- no account system;
- no behavioral tracking;
- no poster binaries committed to GitHub;
- no automatic replacement of maintainer-selected artwork;
- no redesign of the accepted DK Media playback controls.

## Research basis

The plan adapts the useful concepts from Plex's documented metadata/artwork editing and local-media-asset workflows: choosing among artwork, adding artwork from a URL or local/server source, supporting multiple artwork choices, editing metadata, and retaining manual choices rather than blindly replacing them during metadata refresh.


## Plex-parity correction (2026-09-25)

The first search prototype relied too heavily on Wikipedia/Wikimedia Commons. That is not Plex's architecture and is not the target.

Plex uses a scanner plus metadata-agent/provider model. Its current Plex Movie agent performs automatic matching and can use online metadata/artwork providers; Plex documentation also identifies The Movie Database as a metadata source used by Plex agents. Local Media Assets are a parallel source, not the primary substitute for online matching. Plex also generates video-frame artwork as a final fallback.

v2.3 target order is therefore:

1. scan/identify the library item from its known title/year and stable external IDs;
2. query a proper movie/TV metadata provider for the matched title and artwork choices;
3. present alternate provider artwork in Edit Artwork;
4. prefer local artwork when explicitly enabled/available, using Plex-compatible naming such as `poster.jpg`, `poster-2.jpg`, or `Movie Name (Year).jpg`;
5. allow manual image upload/URL as an override;
6. generate a frame from the video as a last-resort fallback when no poster is available;
7. lock explicit maintainer selections against automatic refresh.

Wikipedia/Wikimedia Commons may remain supplementary sources but must not be the main movie-matching engine.
